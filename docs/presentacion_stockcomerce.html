Defensa y Arquitectura del Proyecto Full-Stack

StockCommerce

Plataforma Empresarial de Gestión de Inventario Multitienda, Punto de Venta (POS), Cadena de Suministro y Gobernanza de Seguridad por Riesgo y Alcance.

Capa Backend
Spring Boot 4 + Java 17

Clean Architecture, JPA/Hibernate, Spring Security 6 stateless con JWT, transacciones ACID y eventos reactivos de notificación.

Capa Frontend
Angular 20 + PrimeNG

Standalone Components, arquitectura reactiva con Signals, interceptores HTTP, guards de ruta y tema PrimeNG Aura con alto contraste.

Garantía de Calidad
17 Tests de Integración

100% de pruebas pasando en entorno Spring Boot Test. Cobertura completa de matriz RBAC, rollbacks ante falta de stock y flujo operativo.

Arquitectura y Estructura

Diseño Monorepo y Stack Tecnológico

🖥️ Frontend SPA (Angular 20)
  • • Arquitectura Zoneless: Reactividad pura mediante Angular Signals (Writables y Computed).
  • • State Management: AuthStore, PosStore, TiendaSeleccionadaStore, InventarioStore.
  • • Componentes UI: PrimeNG Aura desacoplado con Tailwind CSS v4.
  • • Seguridad en Cliente: AuthInterceptor inyecta el token Bearer en cada petición.
🛡️ Gateway y Seguridad (RBAC)
  • • JwtAuthenticationFilter: Validación sin estado de tokens criptográficos HMAC-SHA256.
  • • AccessControlService: Motor central de evaluación de permisos y nivel de riesgo.
  • • Data Scoping: Aislamiento de consultas por tienda/depósito asignado al usuario.
  • • OpenAPI 3.1 & Scalar: Documentación interactiva de la API servida en /docs.
⚙️ Backend (Spring Boot 4)
  • • Clean Architecture: Capas Controller → Service → Repository → Model.
  • • Consistencia ACID: Descuento atómico de stock con rollback automático en ventas.
  • • Notificaciones AfterCommit: Disparo de alertas asíncronas solo cuando la transacción confirma.
  • • Base de Datos: H2 en memoria para desarrollo/tests; compatible con PostgreSQL/MySQL.
Estructura Monorepo: stockcomerce/ = backend/ (Maven, Java 17, Spring Boot 4) + frontend/ (Angular CLI, Tailwind v4) + dev.ps1 (Orquestador automatizado).

Gobernanza y Autorización

Matriz de Seguridad RBAC y Alcance de Datos

Rol (RolCodigo) Nivel Riesgo Alcance (Scope) Responsabilidad y Acciones Permitidas Restricciones de Seguridad
ADMIN ALTO GLOBAL (Todas) Gobierno de usuarios, roles, catálogo maestro de productos, costos y tiendas. Sin restricciones (Superusuario)
GERENTE_TIENDA MEDIO Por Tienda / Depósito Gestión comercial y operativa de sus sucursales, compras, inventario y ventas. No puede crear ni alterar usuarios ni roles globales.
ENCARGADO_DEPOSITO MEDIO Solo Depósitos Recepción de compras, despacho/recepción de transferencias, conteos físicos. No accede a ventas POS ni visualiza costos de compra.
CAJERO_VENDEDOR BAJO Solo Tiendas POS Facturación en mostrador, emisión de comprobantes, registro y cobro de apartados. Bloqueado en depósitos, órdenes de compra y reportes.
AUDITOR BAJO GLOBAL (Read-Only) Inspección de auditoría, trazabilidad de movimientos, reportes y dashboards. Solo lectura: HTTP 403 en todo POST, PUT y DELETE.
Mecanismo de Control en Runtime (AccessControlService)
1. Validación de Tipo: El sistema rechaza con HTTP 400 asignaciones incompatibles (ej. Cajero en un DEPOSITO o Encargado en una TIENDA comercial).
2. Aislamiento de Consultas: Los repositorios filtran automáticamente el stock para que cada usuario solo vea los locales donde tiene rol activo.
3. Inmutabilidad de Jerarquía: Un usuario no puede otorgar permisos con nivel de riesgo superior o igual al propio.

Backend · services/ & controller/

Servicios de Negocio y Controladores REST

⚙️ Servicios de Negocio (Interfaces & Impl)
  • • InventarioService: Consulta de existencias, cálculo de disponible = (físico - reservado).
  • • VentaService: Descuento atómico, cálculo de total en servidor, registro de salida.
  • • ApartadoService: Reserva de stock físico para clientes y liquidación de señas.
  • • OrdenCompraService: Ciclo completo de compras y recepción de mercadería.
  • • TransferenciaService: Máquina de estados en 4 pasos para despachos y recepciones.
  • • AjusteConteoService: Conciliación de auditoría física ciega contra inventario lógico.
  • • ReporteService: Métricas agregadas, rotación de productos y alertas de reposición.
  • • NotificacionService: Generación reactiva de alertas post-commit.
🌐 Controladores REST Asegurados
  • • AuthController: /api/auth/login, /api/auth/perfil.
  • • InventarioController: /api/inventario (filtrado automático por alcance).
  • • VentaController: /api/ventas (facturación POS y detalle por tienda).
  • • ApartadoController: /api/apartados (alta, cobro de saldo, cancelación).
  • • OrdenCompraController: /api/ordenes-compra (emisión y recepción en almacén).
  • • TransferenciaController: /api/transferencias (tránsito entre locales).
  • • AjusteConteoController: /api/ajustes-conteo (auditoría de stock).
  • • UsuarioController: /api/usuarios (administración RBAC gobernada).
Frontend · Angular 20

Arquitectura Frontend: Signals, Stores y UI Accesible

🔄 State Management con Signals
  • • AuthStore: Token JWT decodificado, roles, asignaciones de alcance y computed signal isAuthenticated().
  • • TiendaSeleccionadaStore: Sincronización global de la tienda activa seleccionada en el shell.
  • • PosStore: Carrito de compras, cálculo reactivo de totales y verificación de stock en vivo.
🛡️ Protección de Rutas y HTTP
  • • AuthGuard: Verifica autenticación y permisos antes de activar cualquier ruta interna.
  • • AuthInterceptor: Inyección transparente del encabezado Authorization: Bearer <token>.
  • • ErrorInterceptor: Captura global de errores 401 y 403 con mensajes claros y redirección.
🎨 Tema PrimeNG Aura & Contraste
  • • Configuración Explícita: darkModeSelector: '.p-dark' para evitar choques visuales.
  • • Alto Contraste Garantizado: Corrección en styles.css para eliminar textos blancos o grises ilegibles en tablas.
  • • Layout Shell Responsive: Sidebar colapsable, breadcrumbs y badges de estado.

Testing Backend · Seguridad

Suite 1: RbacAlcanceIntegrationTest (6 Tests)

Pruebas end-to-end de autenticación, jerarquía de riesgo y aislamiento por tipo de sucursal contra H2 y Spring Boot WebEnvironment.RANDOM_PORT:

Test 1: accesoSinTokenEsRechazadoYAsignacionesInvalidasFallan

Verifica 401 Unauthorized sin token y bloqueo 400 Bad Request si se asigna un Cajero a un DEPOSITO o un Encargado a una TIENDA.

Test 2: encargadoDepositoOperaSoloSusDepositosSinModificarPreciosNiUsuarios

Garantiza que el Encargado solo ve el stock de sus depósitos autorizados, no puede ver costos de compra ni crear nuevos usuarios.

Test 3: cajeroVendedorSoloFacturaEnSuTiendaSinVerReportesNiCompras

El cajero realiza ventas y apartados en su tienda; cualquier intento de acceder a órdenes de compra o reportes retorna 403 Forbidden.

Test 4: auditorTieneAccesoLecturaGlobalPeroNoPuedeModificarStock

El Auditor puede consultar inventarios y kardex globalmente, pero llamadas de mutación (POST/PUT/DELETE) reciben 403 Forbidden.

Test 5: gerenteTiendaNoPuedeGestionarUsuariosAdminNiCambiarAlcances

Evaluación de nivel de riesgo: un rol MEDIO no puede crear ni modificar usuarios de nivel ALTO (ADMIN).

Test 6: revocacionDeAsignacionInvalidaAccesoEnTiempoReal

Al eliminar la vinculación de un usuario a una tienda, el acceso a sus datos se revoca inmediatamente en la siguiente consulta.

Testing Backend · Flujo Operativo

Suite 2: StockFlowIntegrationTest (10 Tests)

Pruebas de consistencia transaccional ACID, cálculo de stock disponible, alertas reactivas y movimientos:

1. entradaAceptaCantidadPequenaYCreaInventarioConMinimo12
Entrada inicial genera el inventario con umbral de reposición automático en 12 unidades.
2. ventaDescuentaStockRegistraSalidasYUsaPrecioDelProducto
Venta atómica descuenta stock, genera historial de salida y respeta precio oficial maestro.
3. ventaSinStockSuficienteHaceRollbackCompleto
Si se solicitan más unidades de las disponibles, la transacción se revierte al 100% (anti-overbooking).
4. notificaSoloAlCruzarElMinimoDe12HaciaAbajo
Alerta reactiva AfterCommit se genera únicamente cuando el stock cae bajo 12 (12 → 11).
5. ventaFallidaNoGeneraNotificacion
Una venta fallida con rollback no dispara notificaciones falsas al confirmed listener.
6. transferenciaMueveStockEntreTiendas
Despacho en origen y recepción en destino garantizan la conservación de existencias totales.
7. transferenciaSinStockFallaSinModificarNada
No se permite emitir transferencias que excedan el stock físico disponible en origen.
8. salidaPorMermaDescuentaStock
Salidas operativas por rotura o vencimiento decrementan stock con causa auditable.
9. reporteConsolidadoMuestraTotalesCorrectos
Cálculo de ingresos, valorización del inventario y rotación concilian con exactitud matemática.
10. conteoFisicoCorrigeDiscrepanciasConAjuste
Auditoría física ciega genera ajuste compensatorio por diferencia (sobrante o faltante).

Conclusiones de Calidad y Robustez

• Protección Financiera Inviolable: El precio de venta y el stock no pueden ser adulterados por el cliente frontend; el servidor valida y aplica las reglas de negocio sobre la base de datos de manera atómica.
• Trazabilidad de Auditoría Completa: Cada ingreso, venta, transferencia, merma o conteo físico deja un rastro inmutable que puede ser auditado en tiempo real sin inconsistencias.
• Cero Notificaciones Espurias: El uso de @TransactionalEventListener(phase = AFTER_COMMIT) garantiza que una operación fallida nunca dispare falsas alarmas de reposición.
• Experiencia de Usuario sin Fricciones: El frontend mantiene contraste visual óptimo (accesibilidad WCAG), retroalimentación inmediata y navegación basada en el contexto de la sucursal seleccionada.
